Mission 300 Monitoring Dashboard

API Contract — endpoints required from the backend

Every endpoint below is derived directly from the Zod schemas in src/api/schemas/ and is already implemented as a mock, consumed by a working frontend — the shapes here are exercised, not theoretical. If a shape needs to change, change the schema and this document together and flag it: a field added is harmless, a field removed or retyped is a breaking change.

Base URL: everything under /api  ·  Content type: application/json both ways, except two file-upload endpoints (multipart/form-data) and two report-export endpoints (binary download)  ·  Timestamps: ISO 8601 with timezone, e.g. 2025-10-14T09:12:00Z  ·  Errors: non-2xx with { "message": "human readable" } — 404 not found, 400 failed validation/business rule, 401 bad credentials.

Conventions

Rules that apply across every module below, not repeated per endpoint.

  • Empty vs. zero — 0 is a real value and is rendered as 0. null is used only where the schema allows it, and always means "not applicable / not yet approved" — never "zero".
  • Enums are closed sets — a value outside an enum's allowed options fails validation on the frontend. See the shared enumerations table and each module's own enums.
  • lastUpdated appears on nearly every overview payload — it is when the underlying data was last refreshed, not when the response was generated. Shown to the user as "as of …".

Nullability carries meaning

Several fields are nullable on purpose — the distinction is a specification requirement, not a convenience:

  • AccessChannel.target / .percentComplete — null means no approved target exists. Never send 0 here.
  • BulletMetric.target — null means no Compact target is currently stated. .expected — null means no approved trajectory exists.
  • PillarHeadlineCard.rawValue / .target — same rule: no value collected yet, or no approved target yet.
  • KpiProfile.baseline / .current / .target — null means that figure isn't available yet (validationStatus will be future when current is null).
  • ProjectRecord.fundingSource / .evidenceUrl, MilestoneRecord.actualDate / .evidenceUrl — not yet secured / not yet reached / no document attached. Never send an empty string.
  • SubmissionDetail.fileName — null for manual-entry (no uploaded file).
  • EscalationRecord.resolution / .evidenceUrl — null until resolved / until a document is attached.

Pagination envelope

Shared by every paginated list in the product:

{
  "items": [ /* the current page only */ ],
  "page": 1,        // 1-based
  "pageSize": 25,
  "total": 312      // total matching records across ALL pages, not items.length
}

Query params: ?page=1&pageSize=25. pageSize has a per-module maximum (see each module's query table). Sorting is currently client-side over the returned page only — see open question 6.

provenance — required on every metric

All four fields are required, non-empty strings:

{
  "definition":  "What this metric is, and what it is not.",
  "methodology": "How it is calculated, including exclusions.",
  "source":      "Which publication or register it comes from.",
  "lastUpdated": "2025-09-30T00:00:00Z"
}

Pre-formatted display values — a decision the backend should confirm

Several fields are sent pre-formatted as display strings alongside a raw number:

{ "value": "₦2.2tn", "current": 2.2 }
{ "value": "$0.0B",  "current": 0 }
{ "value": "5.4 GW", "availableMw": 5400 }
On reflection this is probably the wrong boundary — it makes the backend own currency/unit formatting and blocks locale or compact-number changes on the frontend without a release. If you'd rather send structured values ({ value, unit, scale, precision }) and let the frontend format them, say so before building against this — cheaper to change now than later.

Data modes

Controlled by build-time environment variables (src/config/environment.ts).

VITE_DATA_MODEBehaviour
mockEvery /api request is intercepted and answered by MSW in the browser. No backend needed — the default in local development.
hybridMSW answers requests for modules without a real backend yet, and proxies requests for finished modules to VITE_SUBMISSIONS_BACKEND_URL. Used for staged one-module-at-a-time rollout.
backendMSW is disabled entirely. Every request goes to VITE_API_BASE_URL for real. This is what production should run once the API implements everything below.

For integration testing: point the API at VITE_API_BASE_URL and set VITE_DATA_MODE=backend. No MSW or mock code needs to change.

1. Authentication

Not yet specified by the product spec in detail, but the frontend implements and depends on a specific two-step login flow — this is the one thing here that is genuinely load-bearing UX, not just a data shape.

POST/api/auth/identify

Step 1 — user enters only their email. Confirms an account exists and returns the display identity used on the password screen, without revealing whether the password is right yet.

Request

{ "email": "a.bello@finance.gov.ng" }

Response 200

{
  "email": "a.bello@finance.gov.ng",
  "displayName": "Aisha Bello",
  "institution": "Federal Ministry of Finance"
}

Response 404

If no active account matches: { "message": "We could not find an active account for that email." }. An account with status !== 'active' must be treated the same as no account — do not confirm suspended/pending accounts exist.

POST/api/auth/login

Step 2, shown only after identify succeeds. Full credential check.

Request

{ "email": "a.bello@finance.gov.ng", "password": "…" }

Response 200

{
  "accessToken": "…",
  "user": {
    "id": "usr-006",
    "name": "Aisha Bello",
    "email": "a.bello@finance.gov.ng",
    "role": "oversight-user"
  }
}

role must be one of the SystemRole enum values — the frontend uses it directly to decide which sidebar sections and routes this user can reach.

Response 401

Wrong password or inactive account: { "message": "The password you entered is incorrect." }. Use one generic message — don't distinguish "wrong password" from "account inactive", to avoid leaking account state.

The frontend stores accessToken and attaches it as a bearer token on every subsequent request once the API expects one (not yet enforced by any schema — see open question 4).

POST/api/auth/forgot-password

Request

{ "email": "…" }

Response 200

Always the same body regardless of whether the email matches an account (prevents account enumeration):

{ "message": "If an active account exists for that email, reset instructions have been sent." }

3. Executive Overview

The Compact leadership view. Schema: src/api/schemas/executive-overview.ts.

GET/api/executive-overview

Query parameters — all optional

ParameterExample
periodq3-2025
pillarlast-mile-access or all
institutionnerc or all

The backend must apply every supplied parameter before returning the payload — the frontend does not calculate KPI values, project totals or progress, it only renders the response. When a filter has no matching records, return empty arrays for the affected sections rather than reusing the unfiltered data.

Response shape (abbreviated)

{
  "lastUpdated": "2025-10-14T09:12:00Z",
  "appliedPillar": "all",
  "headlineCards": { /* Section A — exactly four named cards */ },
  "accessDelivery": [ /* Section B — three channels */ ],
  "nationalPerformance": [ /* Section C — six bullet metrics */ ],
  "deliveryStatus": { /* Section D — projects, chart counts, exceptions */ }
}

appliedPillar — echo the pillar the payload was actually calculated for (all for All Pillars), so the frontend can confirm the server applied what was asked.

Section A — headlineCards (exactly four, named fields, not an array)

FieldCardNotable requirements
peopleWithElectricityAccessPeople with electricity accessbaseline, current, 2030 target on a shared scale (scaleMax > scaleMin, enforced)
accessRateElectricity access ratesourceYear required — an annual official publication, must never read as current-period data. sparkline[], oldest→newest
generationCapacityAvailable generation capacityavailableMw, installedMw, availabilityRatio (0–100), sparkline[] (≥2 points to render a line)
cleanCookingAccessClean cooking accesssame shape as peopleWithElectricityAccess

Every headline card carries an optional trend: { change, label, direction } — when present, rendered as a period-on-period pill. Headline outcomes remain national even when a pillar filter is applied — only Sections C and D narrow to the selected pillar.

Section B — accessDelivery

Three channels, in this order: grid-connections, mini-grid-connections, solar-home-systems. Known targets: 750,000 mini-grid household connections by 2030 (DARES); 2.75 million Solar Home Systems by 2030. Grid connections have no approved target — send target: null, percentComplete: null.

Section C — nationalPerformance

Six bullet metrics, ids: renewable-share, metering-rate, atcc-losses, market-remittance, tariff-shortfall, private-capital. Each carries its own scale (scaleMin/scaleMax, scaleMax > scaleMin enforced) — the metrics aren't comparable. direction must be lower-is-better for atcc-losses and tariff-shortfall — a falling value is an improvement there and renders as such.

Section D — deliveryStatus

  • ongoingProjects[] — rows shared by the searchable table and map views. Exclude completed records. Each row carries id/name, pillar + label, owner, location, latitude/longitude, currentStatus, startDate/endDate. The frontend does not geocode location strings.
  • statusSummary[] — backend-calculated overall counts for on-track, at-risk, delayed, blocked (excludes completed). The donut chart renders these directly.
  • exceptions[] — ranked by severity, delivery impact and days unresolved. The UI displays at most five; sending more is allowed and harmless.
The specification is explicit: count records by status, never average unrelated performance percentages.

4. Public Gateway

The unauthenticated landing page and its "National Progress" drill-down.

This is the one genuinely new endpoint the backend needs to build — it does not exist yet. The frontend today temporarily reads GET /api/executive-overview as a stopgap. Do not treat that as the real contract; anything shown on the public pages today is unreviewed for public release.
GET/api/public/overview not yet implemented
  • No authentication.
  • Serves the headline strip, delivery channels and pillar indicators shown on the public home and progress pages.
  • Every figure still carries validationStatus and provenance — the public version does not get to skip disclosure; if anything it matters more here.
  • Send display labels, not filter slugs, for anything shown as text (e.g. "Q3 2025", not "q3-2025").
  • Cacheable — this is read-only public data and will take the highest traffic volume of anything in the platform. Design for that (e.g. CDN cache with short TTL, or Cache-Control headers).
  • Recommended (not yet locked in — see open question 7): hold back anything not confirmed or public-source validation status from this endpoint specifically, even though the authenticated Executive Overview shows every status.

5. KPI Directory (KPI Explorer)

The authoritative indicator catalogue and technical drill-down. Schema: src/api/schemas/kpi-explorer.ts. The KPI identifier (e.g. M300-P1-003) is first-class here for traceability, but must not appear on executive or pillar cards.

GET/api/kpi-explorer

Query (all optional)

search, pillar, category, readiness, validationStatus, sourceInstitution, reportingPeriod, geography, page, pageSize (max 200).

Response

{
  "lastUpdated": "2025-10-14T09:12:00Z",
  "summary": [ /* Section A — catalogue/readiness counts */ ],
  "catalogue": { "items": [ /* … */ ], "page": 1, "pageSize": 25, "total": 17 },
  "pillarDistribution": [ /* Section D — value coverage by pillar */ ],
  "readinessDistribution": [ /* Section D — Core / Supporting / Future */ ]
}
  • summary and both *Distribution arrays describe the full catalogue, not the filtered slice. Only catalogue is filtered/paginated by the query.
  • validationStatus (per row): confirmed, public-source, requires-validation, provisional, future — future means no value exists yet, a catalogue fact, never presented as confirmed.
  • readiness is core, supporting or future.
  • Each pillarDistribution[].byStatus must sum to that pillar's total.
GET/api/kpi-explorer/kpis/:id

Full profile for one indicator, fetched on demand so the heavy payload isn't loaded for every catalogue row. 404 with { "message": … } for an unknown id.

Four panels' worth of data in one response

  • Metadata — definition, formula, unit, aggregation, frequency, disaggregation, limitations — shown exactly as configured.
  • Values — baseline, current, target (all nullable), matching *Label display strings, varianceLabel (signed, follows direction), history[] (each point: period, value, validationStatus, submissionId nullable — points seeded before submission-tracing existed).
  • Traceability — sourceInstitution, sourceDataset, sourceReference, reportingPeriod, validationStatus, validationDecision, version, confidence, provenance.
  • linkedRecords[] — delivery records (programme/project/ milestone/action) joined through the indicator identifier: type, title, institution, status.
GET/api/kpi-explorer/filters

This module's own eight filter option lists: pillars, categories, readinessTiers, validationStatuses, sourceInstitutions, reportingPeriods, geographies (same { value, label }[] shape as global filters, but this module does not use the global dashboard filter bar).

6. Pillar Dashboards

Deliberately has no entities of its own — a pillar dashboard is a filtered view over data that exists elsewhere. Schema: src/api/schemas/pillar-dashboard.ts.

GET/api/pillars/:pillar

:pillar is one of the six PillarId values.

Response

{
  "pillar": "generation-network",
  "label": "Generation & Network",
  "lastUpdated": "2025-10-14T09:12:00Z",
  "headlineCards": [ /* exactly 4 — real KpiProfile-sourced cards for this pillar */ ],
  "deliveryStatus": { "counts": [ /* by ExecutionStatus */ ], "total": 6 },
  "bottlenecks": [ /* ranked top-5 open bottlenecks for this pillar */ ],
  "kpis": [ /* every KPI Directory catalogue row tagged to this pillar */ ]
}
  • headlineCards — exactly 4. Each carries kpiId (join key back to KPI Directory, not displayed on the card itself, only used for linking), rawValue/target nullable per the usual rule, validationStatus, provenance.
  • bottlenecks — max 5, using the lighter bottleneckRecordSchema shape from the Bottlenecks module.
  • kpis — every catalogue row tagged to this pillar, not just the four headline ones.

The endpoint contract is identical for all six pillars — which ones are enabled in the frontend sidebar is a rollout sequencing decision, not a backend one.

8. Bottlenecks & Exceptions

The full delivery-constraint register — richer than the lightweight shapes shown elsewhere. Schema: src/api/schemas/bottlenecks.ts.

This module's RegisterSeverity (critical/high/ medium/low) is a different enum from Executive Overview's BottleneckSeverity (critical/regulatory/ delayed/blocked) — they answer different questions for different audiences. Do not conflate them.
GET/api/bottlenecks

Query (all optional)

search, severity, category, institution, pillar, linkedRecord, lifecycleStage, escalationStatus, validationStatus, reportingPeriod, plus page, pageSize (max 200), and escalationPage — the register and the escalation tracker paginate independently even though both come back in the same payload.

Response

{
  "lastUpdated": "2025-10-14T09:12:00Z",
  "alerts": [ /* exactly 4 headline alert cards */ ],
  "register": { "items": [ /* … */ ], "page": 1, "pageSize": 25, "total": 90 },
  "byCategory": [ /* Section C */ ],
  "byLifecycleStage": [ /* Section C */ ],
  "byInstitution": [ /* Section D */ ],
  "escalations": { "items": [ /* … */ ], "page": 1, "pageSize": 25, "total": 12 }

  • byCategory / byLifecycleStage / byInstitution — aggregate counts over the full register, not the filtered/paginated page.
  • escalations — bottleneckId (join key), decisionRequired, level (programme-management/ institution-leadership/steering-committee/ministerial), owner, dueDate, daysOverdue, status, resolution (nullable), evidenceUrl (nullable).

9. Data Submissions

The full submission → validation → calculation → approval → KPI-publish pipeline. The module with the most operational business logic in the product — read it carefully. Schemas: src/api/schemas/data-submissions/ (split across common.ts, obligations.ts, submissions.ts, compliance.ts, filters.ts).

Shared workflow vocabulary

Every list item across this module carries a status: WorkflowStatus object, not a bare string:

{ "code": "pending-review", "label": "Pending review", "tone": "warning" }

code is one of: due, draft, validation-failed, ready, pending-review, returned, rejected, provisional, approved, overdue, missing, open, in-progress, resolved. tone is one of neutral/info/ warning/danger/success — the frontend colours the status pill from tone, not by re-deriving meaning from code, so send the tone matching the severity intended.

Every list item also carries availableActions: WorkflowAction[] — enter-data, upload-template, view, review, download-template, correct, submit, contact-owner. The backend decides which actions are available for a given row's current state — the frontend renders exactly the buttons this array lists, it does not compute availability itself.

GET/api/data-submissions/filters

Eight groups: institutions, datasets, reportingPeriods, submissionStatuses, validationStatuses, reviewers, readinessTiers, overdueStatuses.

GET/api/data-submissions/obligations

The reporting-obligation register — what each institution owes, by when.

Query

search, institution, dataset, reportingPeriod, submissionStatus, validationStatus, reviewer, readinessTier, overdueStatus, page, pageSize (max 100).

Response

Paginated Obligation[] — institution, dataset, reportingPeriod, frequency, dueDate, dueLabel (e.g. "Due in 5 days"), status, template: { id, version, fileName, downloadUrl }, acceptedSubmissionId (nullable — the submission currently fulfilling this obligation, once approved/provisional), availableActions.

GET/api/data-submissions/obligations/:id/entry

Returns the manual-entry form definition for this obligation — title, institution, dataset, reportingPeriod, sections[], each with fields[] (id, label, helpText, type (text/number/date/select/textarea), required, unit (nullable), placeholder, options for select fields). The form is entirely server-driven — the frontend renders whatever fields are sent.

POST/api/data-submissions/obligations/:id/entry

Submits manual entry.

Request

{ "values": { "<fieldId>": "<string>", ... }, "sourceReference": "…", "notes": "…" }

All values are sent as strings regardless of the field's type — the backend parses/validates by type.

Response 201

{ "submissionId": "…", "version": 1, "status": { "code": "pending-review", … }, "message": "…", "nextUrl": "/data-submissions/validation/…" }
GET/api/data-submissions/obligations/:id/upload

Returns the upload definition — institution, dataset, reportingPeriod, template (same shape as above), acceptedFileTypes[] (e.g. ['.xlsx']), acceptedFileTypesLabel, maxFileSizeMb.

POST/api/data-submissions/obligations/:id/upload multipart/form-data

Form fields

FieldRequiredNotes
fileyesThe completed template. 400 if missing.
sourceReferenceyes400 if blank.
notesnoDefaults to empty string.

Response 201

Same shape as the manual-entry response above (submissionId, version, status, message, nextUrl).

Backend responsibility, not the frontend's: parsing the uploaded file, validating every row against the dataset's field definitions, running the dataset's calculation formula, and producing the extractedValues shown on the review screen. The frontend does not calculate KPI values from an upload — it only uploads the file and displays what the backend computed.
GET/api/data-submissions/templates/:fileName

Downloads the current template workbook for a dataset, generated fresh from the dataset's current field configuration (so adding a field changes the downloadable template with no separate release). Returns Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet.

GET/api/data-submissions/submissions

Query

search, institution, dataset, reportingPeriod, submissionStatus, page, pageSize.

Response

Paginated SubmissionListItem[] — method (manual-entry/template-upload/api), methodLabel, version, submittedBy, submittedAt (nullable — null for a draft never submitted), submittedAtLabel, status, validationSummary (free text), plus institution/dataset/reportingPeriod/ availableActions.

GET/api/data-submissions/validation

The review queue. Query: same as /submissions, plus (implicitly) only rows awaiting a decision.

Response

Paginated ValidationQueueItem[] — extends SubmissionListItem with reviewer, ageLabel, automatedCheck (a WorkflowStatus — pass/fail of the backend's automated validation pass), issueCount.

GET/api/data-submissions/validation/:id

Full review detail — extends ValidationQueueItem with:

  • fileName (nullable — null for manual entry).
  • issues[] — type, location, field, message, requiredCorrection — every failed validation rule the backend found, specific enough that a reviewer or submitter can act on it without guessing.
  • history[] — every status transition, with actor, occurredAt, comment.
  • permittedDecisions[] — subset of ['approved', 'provisional', 'returned', 'rejected']. The backend decides which decisions are legal from the current state (e.g. unresolved critical issues should not permit approved) — the frontend only shows buttons for what's in this array.
  • extractedValues[] — kpiId, kpiName, reportingPeriod, value — what publishing this submission would write to which KPI, shown to the reviewer before they decide, and echoed back in the decision response below.
POST/api/data-submissions/validation/:id/decisions

Records a reviewer's decision.

Request

{ "decision": "approved" | "provisional" | "returned" | "rejected", "comments": "…" }

comments min 3 chars — 400 if shorter, and reject if decision is not in this submission's current permittedDecisions.

Response 200

{
  "submissionId": "…",
  "status": { "code": "approved", … },
  "message": "Decision recorded: Approved. Published to Metering Rate.",
  "nextUrl": "…",
  "published": [ /* empty for 'returned'/'rejected', or if nothing was extracted */ ]
}
This is the point where a KPI's current value and history actually change. approved and provisional decisions publish every entry in extractedValues to its KPI (updates KpiProfile.current, appends a KpiHistoryPoint with submissionId set to this submission, and should also update the obligation's acceptedSubmissionId). returned and rejected publish nothing. The published array in the response should reflect exactly what was written.
GET/api/data-submissions/overdue

Paginated OverdueItem[] — obligations past their dueDate with no accepted submission. overdueLabel (e.g. "12 days overdue"), owner, status, availableActions.

GET/api/data-submissions/gaps

Paginated DataGap[] — KPIs with no submission ever received for the current period. kpiId, kpiName, pillar, category, readinessTier, owner, nextAction.

10. State & DisCo

Six separate endpoints rather than one parameterised view. Schemas split across src/api/schemas/state-disco/. Every response wraps its rows in a shared meta block (title, description, lastUpdatedLabel, sourceLabel) so each view can carry its own framing text even though the page shell is shared.

GET/api/state-disco/filters

Eight groups: reportingPeriods, views, distributionCompanies, states, utilityMetrics, serviceBands, validationStatuses, sources.

GET/api/state-disco/overview
{ "meta": { … }, "selectedUtility": "…", "metrics": [ /* exactly 4 */ ] }

Each metric: value, supportingLabel, benchmarkLabel, varianceLabel, progressPercent (0–100), trend (required), provenance.

GET/api/state-disco/comparison

Query: distributionCompany — a DisCo id, or national (the sentinel for "all DisCos", not all — this one endpoint's convention differs from every other module, match it exactly). Rows carry pre-computed display strings for active/metered/unmetered customers, metering rate, energy received/billed + billing efficiency, revenue billed/collected + collection efficiency, remittance performance, plus paired bar-percent fields (energyReceivedBarPercent, energyBilledBarPercent, revenueBilledBarPercent, revenueCollectedBarPercent, each 0–100) driving the comparison bars.

GET/api/state-disco/supply-tariff

Query: distributionCompany (same convention as /comparison). Rows: utility, effectiveOrder, and exactly 5 bands (band A–E plus supplyHours, tariff, intensityPercent). No unweighted tariff average across bands.

GET/api/state-disco/delivery

Query: distributionCompany (same convention as above). Rows: milestone, dueDateLabel, executionStatus, achievedLabel, evidenceLabel, reportingCompliance, bottleneck (free text, may be empty).

GET/api/state-disco/states

Query: state (a state id, or all/omitted for every state). Rows: state, zone, miniGridConnections, solarHomeSystems, activeProgrammes, activeProjects, openBottlenecks, validationLabel, coverageBarPercent (0–100). Also carries a notice string — connection counts must not be converted into an inferred state electricity-access rate.

GET/api/state-disco/states/:id

Single-state detail — the matching coverage row plus records[] (type — programme/project/bottleneck — name, owner, status, deliveryLabel, sourceLabel). 404 if the state id doesn't exist.

11. Reports & Exports

Schema: src/api/schemas/reports.ts. The spec groups reports into four categories (compact, performance, delivery, data-governance), each containing one or more report types — a report type, not a category, is what a user actually generates or finds in Saved Reports.

GET/api/reports/filters

Ten groups, including exportFormats (pdf/xlsx).

GET/api/reports

POST/api/reports/preview

Request

reportType, period, pillar, kpiCategory, state, distributionCompany, programmeOrAgency, validationStatus, readinessTier, format. 400 on a schema mismatch.

12. Administration (User Access)

Schema: src/api/schemas/administration.ts. This module is account/permission administration, not performance measurement.

GET/api/administration

Query

search (name/email/institution), institution, role, accountStatus, permission, accessScope, module, auditPeriod.

Response

{
  "lastUpdated": "…",
  "summary": [ /* accessSummaryCardSchema[] */ ],
  "users": { "items": [ /* userAccountSchema[] */ ], … },
  "roles": [ /* roleDefinitionSchema[] — all 7, not paginated */ ],
  "scopeAssignments": { "items": [ /* … */ ], … },
  "auditLog": { "items": [ /* … */ ], … }
}
  • summary[] — each carries breakdown[] (label/count pairs) and elevated: boolean — true marks the one card needing visual emphasis.
  • users[] — role is one of the seven SystemRole values, status one of active/pending/ inactive/suspended, lastLogin nullable.
  • roles[] — the role × permission matrix: permissions[] (subset of the seven Permission values), modules[] (free-text module names this role can reach), assignedUsers (live count, not static).
  • scopeAssignments[] — a user's responsibility pinned to a scopeLevel (national/state/ distribution-company/institution/programme/ project/dataset/indicator) and a specific scope string. effectiveTo nullable.
  • auditLog[] — recordId/priorValue/newValue all nullable, result one of success/failure/ rejected.
GET/api/administration/filters

Seven groups: institutions, roles, accountStatuses, permissions, accessScopes, modules, auditPeriods. This module has its own filters — the global filter bar does not apply here.

POST/api/administration/users/invite

Request

name, email, institution, designation, role, accessScope (a ScopeLevel), invitationMessage (optional, max 500 chars).

Response 201

{ "user": { /* userAccountSchema */ }, "message": "…" }

The new account, status pending until the invitee accepts.

limited-data and provisional (DeliveryStatus) are not performance judgements — they mean the dashboard cannot yet assert how something is performing. A pillar with no KPIs assigned must not be presented as failing.

MetricIconName is a semantic name, not an icon — the frontend maps it to a glyph internally, so the backend never needs to know about the icon library.

15. Open questions for the backend team

  1. Pillar-specific headline cards — which two metrics should replace the middle cards for each of the six pillars? Blocks full dynamic pillar-headline behaviour; today all four are the same generic shape for every pillar.
  2. Pre-formatted values — keep the display-string convention, or move to structured values ({ value, unit, scale, precision }) with formatting owned by the frontend?
  3. Filter reach — resolved for Executive Overview: only reporting period, Compact pillar and institution are accepted there. Every other module has its own separate filter set, documented in that module's section — confirm you're building against each module's own list.
  4. Auth scheme — the two-step identify/login flow is settled UX. Not yet settled: whether accessToken is a JWT, how long it lives, whether there's a refresh flow, and the exact header (Authorization: Bearer <token> is assumed but not yet confirmed).
  5. Pagination — resolved. ?page=1&pageSize=25 → { items, page, pageSize, total }, used identically everywhere paginated. Please implement exactly as specified, including total being the full matching count, not items.length.
  6. Sorting — currently client-side over the returned page only, so sorting page 1 of a paginated table sorts 25 rows, not the full result set. To sort properly, server side sorting is needed — proposal: ?sort=<column>&order=asc|desc, with <column> matching the response field name exactly. Confirm which columns will be accepted per module.
  7. Public Gateway data threshold — should GET /api/public/overview return every KPI regardless of validation status, or hold back anything not confirmed/public-source? Recommended default is the latter, not yet locked in.
  8. GET /api/public/overview — the one wholly new endpoint this contract requires that doesn't exist as a mock yet.
