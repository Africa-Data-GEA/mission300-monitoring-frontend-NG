Mission 300 Monitoring Dashboard

API Contract — endpoints required from the backend

Every endpoint below is derived directly from the Zod schemas in src/api/schemas/ and is already implemented as a mock, consumed by a working frontend — the shapes here are exercised, not theoretical. If a shape needs to change, change the schema and this document together and flag it: a field added is harmless, a field removed or retyped is a breaking change.

Base URL: everything under /api  ·  Content type: application/json both ways, except two file-upload endpoints (multipart/form-data: data-submissions upload and the branding logo) and one binary-download endpoint (the data-submissions template file — see §10). Reports & Exports (§12) does not return a binary — see the note on that section; the frontend builds the downloadable PDF/XLSX client-side from JSON.  ·  Timestamps: ISO 8601 with timezone, e.g. 2025-10-14T09:12:00Z  ·  Errors: non-2xx with { "message": "human readable" } — 404 not found, 400 failed validation/business rule, 401 bad credentials.

Last synced with the codebase: 2026-08-08, against every file under src/api/schemas/ and src/mocks/handlers/. This is a hand-maintained document, not generated — if a schema file changes after this date and this stamp hasn't moved, treat the schema as the source of truth and flag the drift.

Global data format — read this first

This section is the actual contract: the shapes and rules every response from every module must follow, regardless of what that module's data is about. The module-by-module sections after this one (3 onward) describe what each endpoint returns; this section describes the format that response has to be in to be usable by the frontend — the envelope, the required metadata block, the meaning of null, and so on. Get this section right and every module below is just filling in fields; get it wrong and no module will parse.

  • Empty vs. zero — 0 is a real value and is rendered as 0. null is used only where the schema allows it, and always means "not applicable / not yet approved" — never "zero".
  • Enums are closed sets — a value outside an enum's allowed options fails validation on the frontend. See the shared enumerations table and each module's own enums.
  • lastUpdated appears on nearly every overview payload — it is when the underlying data was last refreshed, not when the response was generated. Shown to the user as "as of …".

Nullability carries meaning

Several fields are nullable on purpose — the distinction is a specification requirement, not a convenience:

  • AccessChannel.target / .percentComplete — null means no approved target exists. Never send 0 here.
  • BulletMetric.target — null means no Compact target is currently stated. .expected — null means no approved trajectory exists.
  • PillarHeadlineCard.rawValue / .target — same rule: no value collected yet, or no approved target yet.
  • KpiProfile.baseline / .current / .target — null means that figure isn't available yet (validationStatus will be future when current is null).
  • ProjectRecord.fundingSource / .evidenceUrl, MilestoneRecord.actualDate / .evidenceUrl — not yet secured / not yet reached / no document attached. Never send an empty string.
  • SubmissionDetail.fileName — null for manual-entry (no uploaded file).
  • EscalationRecord.resolution / .evidenceUrl — null until resolved / until a document is attached.

Pagination envelope

Shared by every paginated list in the product:

{
  "items": [ /* the current page only */ ],
  "page": 1,        // 1-based
  "pageSize": 25,
  "total": 312      // total matching records across ALL pages, not items.length
}

Query params: ?page=1&pageSize=25. pageSize has a per-module maximum (see each module's query table). Sorting is currently client-side over the returned page only — see open question 6.

provenance — required on every metric

All four fields are required, non-empty strings:

{
  "definition":  "What this metric is, and what it is not.",
  "methodology": "How it is calculated, including exclusions.",
  "source":      "Which publication or register it comes from.",
  "lastUpdated": "2025-09-30T00:00:00Z"
}

Pre-formatted display values — a decision the backend should confirm

Several fields are sent pre-formatted as display strings alongside a raw number:

{ "value": "₦2.2tn", "current": 2.2 }
{ "value": "$0.0B",  "current": 0 }
{ "value": "5.4 GW", "availableMw": 5400 }
On reflection this is probably the wrong boundary — it makes the backend own currency/unit formatting and blocks locale or compact-number changes on the frontend without a release. If you'd rather send structured values ({ value, unit, scale, precision }) and let the frontend format them, say so before building against this — cheaper to change now than later.

Data modes

Controlled by build-time environment variables (src/config/environment.ts).

VITE_DATA_MODEBehaviour
mockEvery /api request is intercepted and answered by MSW in the browser. No backend needed — the default in local development.
hybridMSW answers requests for modules without a real backend yet, and proxies requests for finished modules to VITE_SUBMISSIONS_BACKEND_URL. Used for staged one-module-at-a-time rollout.
backendMSW is disabled entirely. Every request goes to VITE_API_BASE_URL for real. This is what production should run once the API implements everything below.

For integration testing: point the API at VITE_API_BASE_URL and set VITE_DATA_MODE=backend. No MSW or mock code needs to change.

1. Authentication

Not yet specified by the product spec in detail, but the frontend implements and depends on a specific two-step login flow — this is the one thing here that is genuinely load-bearing UX, not just a data shape.

POST/api/auth/identify

Step 1 — user enters only their email. Confirms an account exists and returns the display identity used on the password screen, without revealing whether the password is right yet.

Request

{ "email": "a.bello@finance.gov.ng" }

Response 200

{
  "email": "a.bello@finance.gov.ng",
  "displayName": "Aisha Bello",
  "institution": "Federal Ministry of Finance"
}

Response 404

If no active account matches: { "message": "We could not find an active account for that email." }. An account with status !== 'active' must be treated the same as no account — do not confirm suspended/pending accounts exist.

POST/api/auth/login

Step 2, shown only after identify succeeds. Full credential check.

Request

{ "email": "a.bello@finance.gov.ng", "password": "…" }

Response 200

{
  "accessToken": "…",
  "user": {
    "id": "usr-006",
    "name": "Aisha Bello",
    "email": "a.bello@finance.gov.ng",
    "role": "oversight-user"
  }
}

role must be one of the SystemRole enum values — the frontend uses it directly to decide which sidebar sections and routes this user can reach.

Response 401

Wrong password or inactive account: { "message": "The password you entered is incorrect." }. Use one generic message — don't distinguish "wrong password" from "account inactive", to avoid leaking account state.

The frontend stores accessToken and attaches it as a bearer token on every subsequent request once the API expects one (not yet enforced by any schema — see open question 4).

POST/api/auth/forgot-password

Request

{ "email": "…" }

Response 200

Always the same body regardless of whether the email matches an account (prevents account enumeration):

{ "message": "If an active account exists for that email, reset instructions have been sent." }

Section B — accessDelivery

Section C — nationalPerformance

Six bullet metrics, ids: renewable-share, metering-rate, atcc-losses, market-remittance, tariff-shortfall, private-capital. Each carries its own scale (scaleMin/scaleMax, scaleMax > scaleMin enforced) — the metrics aren't comparable. direction must be lower-is-better for atcc-losses and tariff-shortfall — a falling value is an improvement there and renders as such.

Section D — deliveryStatus

  • ongoingProjects[] — rows shared by the searchable table and map views. Exclude completed records. Each row carries id/name, pillar + label, owner, location, latitude/longitude, currentStatus, startDate/endDate. The frontend does not geocode location strings.
  • statusSummary[] — backend-calculated overall counts for on-track, at-risk, delayed, blocked (excludes completed). The donut chart renders these directly.
  • exceptions[] — ranked by severity, delivery impact and days unresolved. The UI displays at most five; sending more is allowed and harmless.
The specification is explicit: count records by status, never average unrelated performance percentages.

4. Public Gateway

The unauthenticated landing page and its "National Progress" drill-down.

This is the one genuinely new endpoint the backend needs to build — it does not exist yet. The frontend today temporarily reads GET /api/executive-overview as a stopgap. Do not treat that as the real contract; anything shown on the public pages today is unreviewed for public release.
GET/api/public/overview not yet implemented
  • No authentication.
  • Serves the headline strip, delivery channels and pillar indicators shown on the public home and progress pages.
  • Every figure still carries validationStatus and provenance — the public version does not get to skip disclosure; if anything it matters more here.
  • Send display labels, not filter slugs, for anything shown as text (e.g. "Q3 2025", not "q3-2025").
  • Cacheable — this is read-only public data and will take the highest traffic volume of anything in the platform. Design for that (e.g. CDN cache with short TTL, or Cache-Control headers).
  • Recommended (not yet locked in — see open question 7): hold back anything not confirmed or public-source validation status from this endpoint specifically, even though the authenticated Executive Overview shows every status.

Every list item across this module carries a status: WorkflowStatus object, not a bare string:

code is one of: due, draft, validation-failed, ready, pending-review, returned, rejected, provisional, approved, overdue, missing, open, in-progress, resolved. tone is one of neutral/info/ warning/danger/success — the frontend colours the status pill from tone, not by re-deriving meaning from code, so send the tone matching the severity intended.

Every list item also carries availableActions: WorkflowAction[] — enter-data, upload-template, view, review, download-template, correct, submit, contact-owner. The backend decides which actions are available for a given row's current state — the frontend renders exactly the buttons this array lists, it does not compute availability itself.

16. Open questions for the backend team

  1. Pillar-specific headline cards — which two metrics should replace the middle cards for each of the six pillars? Blocks full dynamic pillar-headline behaviour; today all four are the same generic shape for every pillar.
  2. Pre-formatted values — keep the display-string convention, or move to structured values ({ value, unit, scale, precision }) with formatting owned by the frontend?
  3. Filter reach — resolved for Executive Overview: only reporting period, Compact pillar and institution are accepted there. Every other module has its own separate filter set, documented in that module's section — confirm you're building against each module's own list.
  4. Auth scheme — the two-step identify/login flow is settled UX. Not yet settled: whether accessToken is a JWT, how long it lives, whether there's a refresh flow, and the exact header (Authorization: Bearer <token> is assumed but not yet confirmed).
  5. Pagination — resolved. ?page=1&pageSize=25 → { items, page, pageSize, total }, used identically everywhere paginated. Please implement exactly as specified, including total being the full matching count, not items.length.
  6. Sorting — currently client-side over the returned page only, so sorting page 1 of a paginated table sorts 25 rows, not the full result set. To sort properly, server side sorting is needed — proposal: ?sort=<column>&order=asc|desc, with <column> matching the response field name exactly. Confirm which columns will be accepted per module.
  7. Public Gateway data threshold — should GET /api/public/overview return every KPI regardless of validation status, or hold back anything not confirmed/public-source? Recommended default is the latter, not yet locked in.
  8. GET /api/public/overview — the one wholly new endpoint this contract requires that doesn't exist as a mock yet.
