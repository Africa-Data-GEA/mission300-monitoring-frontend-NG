1. Introduction

1.1 What This Is

The M300 Dashboard is a monitoring and evaluation tool for Nigeria's Mission 300 National Energy Compact - the country-level commitment tracking progress toward universal electricity access. It's built for Compact leadership, sector regulators (NERC, REA, TCN), Distribution Companies (DisCos), donor institutions (GEAPP), and through a planned public gateway - Nigerian citizens.

The project is explicitly, deliberately frontend-first: it is a fully working application today, running entirely against browser-based mocks that encode the real API contract, while the actual backend is built separately by the GEAPP backend team against the contract this repo defines and publishes.

1.2 A Deliberately Unusual Status: "Demonstration System"

This is the single most important thing to understand before touching the code. Per the README:

The application is currently a demonstration system: completed API modules can use the NestJS demo backend while unfinished modules remain backed by deterministic browser mocks.

This isn't a prototype that will be thrown away - it's the living specification. The Zod schemas in src/api/schemas/ are the authoritative contract; the mocks satisfy them; the real backend is being built to match them. The project's own architecture boundary note makes the division of responsibility explicit:

The frontend presents values returned by API contracts. KPI calculations, submission validation, approval transitions, aggregation, baselines and target progress are backend responsibilities. Browser mocks illustrate the expected contracts and must not be treated as an authoritative production data source.

Anyone extending this app needs to internalize that boundary: if you find yourself computing a KPI value, an aggregate, or a status transition in a React component, that's very likely a sign the logic belongs in a mock handler standing in for backend work, not in the UI layer.

1.3 Stack Snapshot

Vite + React 19 + TypeScript, TanStack React Query for server state, React Router 8 (data router / createBrowserRouter), Tailwind CSS 4, Radix UI primitives, ApexCharts for data visualization, Zod for schema validation (both env config and every API response), MSW (Mock Service Worker) for the browser-mock layer, Vitest + Testing Library for tests, ESLint + Husky for quality gates, @react-pdf/renderer and exceljs for report export.

2. System Architecture

2.1 The Three Data Modes

The whole architecture pivots on one environment variable, VITE_DATA_MODE, with three values:

Mode Behavior
mock Every /api request is intercepted and answered in-browser by MSW. No backend needed at all. Default for local dev and for CI.
hybrid MSW still intercepts /api, but for modules the real backend already implements, it proxies the request through to VITE_SUBMISSIONS_BACKEND_URL instead of answering from mock data. Everything else still gets a mock answer. Used only for the demonstration deployment while backend coverage is incomplete.
backend MSW is disabled entirely. Every request goes straight to VITE_API_BASE_URL. This is the target production configuration once the real backend implements the full contract.

This lets the frontend team ship a fully-functional demo before a single backend endpoint exists, then migrate module-by-module to hybrid, then flip to backend once coverage is complete - without ever changing a component.

2.2 Mode Resolution Logic

src/config/environment.ts resolves the effective mode with a specific precedence, validated by a Zod schema so a malformed .env fails loudly at startup rather than silently misbehaving:

1. Test runner (vitest) → always 'mock', regardless of env vars
2. Explicit VITE_DATA_MODE, if set
3. Legacy VITE_ENABLE_MOCKS flag (kept for backward compatibility):
   - 'true'  + VITE_SUBMISSIONS_BACKEND_URL set → 'hybrid'
   - 'true'  + no backend URL                    → 'mock'
   - 'false'                                     → 'backend'
4. Fallback: DEV build → 'mock' (or 'hybrid' if a submissions URL is present)
             non-DEV build → 'backend'

hybrid mode without VITE_SUBMISSIONS_BACKEND_URL set throws at startup - this is a deliberate fail-fast rather than a silent fall-through to mock behavior that would mask a misconfiguration.

2.3 Request Flow (all modes)

Every network call, regardless of mode, goes through one function: src/lib/api-client.ts's request<T>(). This single choke point is deliberate - it's where auth headers, base URL resolution, error normalization, and (critically) response schema validation all live, so no call site can bypass any of them.

Component
   │
   ▼
React Query hook (src/features/<feature>/hooks or similar)
   │
   ▼
api.get/post/put/patch/delete(path, schema, options)
   │
   ▼
request<T>()  - src/lib/api-client.ts
   │  BASE_URL = '/api' if usesBrowserMocks, else VITE_API_BASE_URL
   │
   ▼
fetch(...)
   │
   ├─ mock/hybrid mode → intercepted by MSW service worker in the browser
   │                       (src/mocks/browser.ts registers src/mocks/handlers.ts)
   │
   └─ backend mode → real network request to the configured API host
   │
   ▼
response.ok? ──── no ──→ throw ApiError(status, message, body)
   │ yes
   ▼
content-type is JSON? ── no ──→ throw ContractError (almost always means the
   │ yes                        mock worker isn't running / dev server
   ▼                            returned the SPA shell instead of JSON)
schema.safeParse(payload)
   │
   ├─ fails → throw ContractError naming every offending field path
   └─ passes → return the validated, correctly-typed data

Why this matters: a ContractError is not a generic failure - it's specifically the frontend and a (real or mock) backend disagreeing about the shape of a response, and the error message names the exact field paths that don't match. This makes contract drift between frontend expectations and backend reality loud and immediate rather than a silent undefined deep in a component tree.

2.5 Why Zod Everywhere

Zod schemas do triple duty in this codebase, and this is the architectural idea worth understanding before working in it:

  1. Runtime contract enforcement - every API response is validated against its schema before a component ever sees it (§2.3).
  2. Compile-time types - TypeScript types are z.infer'd from the same schemas, so the type and the runtime check can never drift apart the way a hand-maintained interface alongside a separate validator could.
  3. Documentation source of truth - docs/api-documentation.html is explicitly written against the schemas (not the other way around), and docs/database-structure.md states plainly that Contract file column points at the exact schema file that owns each shape.

This means src/api/schemas/ is the single place to look to know, with certainty, what any endpoint actually returns - more reliable than any hand-written doc, including this one.

3. Getting Started (Local Development)

# 1. Install dependencies (pnpm is the only supported package manager - see
#    packageManager in package.json and pnpm-lock.yaml)
pnpm install

# 2. Copy env template
cp .env.example .env.local

# 3. Run - defaults to mock mode, no backend required
pnpm dev

Runs at http://localhost:5173. The mock service worker (src/mocks/browser.ts) registers automatically in dev/mock mode - if you ever see a 2xx response that isn't JSON, the most likely cause (per the api-client's own error message) is that the mock worker didn't register; hard-reload the page.

4. Core Concepts

4.1 The Six Compact Pillars

Every module in the app organizes around six fixed pillars (PillarId enum, src/api/schemas/common.ts):

  1. generation-network
  2. last-mile-access
  3. financially-viable-utilities
  4. private-sector-participation
  5. regional-integration
  6. clean-cooking

Of the six, only Generation & network and Last-mile access currently have a built-out pillar dashboard (READY_PILLARS in src/config/navigation.ts) - the other four are visible in navigation (so the full information architecture is reviewable) but rendered disabled, per the project's own convention of not pretending unbuilt pages exist.

4.2 Status & Confidence Vocabularies - Closed, Not Free Text

Three enums are deliberately closed unions rather than open strings, because their colors and meaning are contractually fixed across frontend and backend:

  • DeliveryStatus - completed / on-track / at-risk / lagging / delayed / blocked / limited-data / provisional
  • DataConfidence - confirmed / requires-validation / future-gap
  • SourceTag - live / live-cpr / public-source / indicative / requires-validation

Adding a new status value is explicitly documented as a contract change, not a styling tweak: it requires updating the union, the color map in status-badge.tsx, docs/api-documentation.html, and the page specification together.

The most important nuance in the whole vocabulary: limited-data and provisional are deliberately styled neutral, never red. They mean "the dashboard cannot yet assert how something is performing" - which is categorically different from "this is failing." A pillar with no KPIs assigned yet must never render as if it's underperforming.

4.3 Trend Direction Is Metric-Specific

ImprovementDirection (higher-is-better / lower-is-better) is carried on nearly every metric, because a rising number isn't always good news. ATC&C losses and tariff shortfall are lower-is-better - for those, a falling value renders with a green up-is-bad-down-is-good arrow logic (src/lib/trend.ts). Getting this backwards on a regulator-facing dashboard would actively mislead the reader, which is presumably why the contract makes direction mandatory per-metric rather than assuming one global convention.

4.4 Nullability Is Meaningful, Not Absence

docs/api-documentation.html is explicit that several null values are semantically loaded, not "no data yet":

  • AccessChannel.target / percentComplete - null means no approved target exists (the spec forbids deriving a grid-connection target from the national 9% access-rate commitment). The UI must show trend only, no progress bar - sending 0 here would be actively wrong, implying a target of zero.
  • BulletMetric.target - null means no Compact target is currently stated for that metric (e.g. ATC&C losses).
  • BulletMetric.expected - null means no approved trajectory exists for the period.

Similarly, 0 is always a real value and renders as 0 - it is never used as a stand-in for "no data."

4.5 Provenance Is Mandatory, Not Optional Metadata

Every metric in the contract carries a required provenance object:

{
  "definition":  "What this metric is, and what it is not.",
  "methodology": "How it is calculated, including exclusions.",
  "source":      "Which publication or register it comes from.",
  "lastUpdated": "2025-09-30T00:00:00Z"
}

All four fields are required, non-empty strings. This isn't decorative - docs/api-documentation.html states plainly that the dashboard's credibility rests on every figure disclosing where it came from, and several KPIs carry specific caveats that must reach the reader (e.g., that milestone delivery is an implementation measure, not an average of all KPIs; that renewable generation share is seasonal).

4.6 Two Open Design Questions Still Live in the Contract

docs/api-documentation.html documents, rather than hides, two unresolved decisions the frontend team is waiting on the backend/spec owner to answer:

  1. Pre-formatted display strings vs. structured values. Several fields currently arrive pre-formatted ({"value": "₦2.2tn", "current": 2.2}), which the frontend team has flagged as "the wrong boundary" - it makes the backend own currency/unit formatting and blocks locale changes. The proposed alternative is a structured {value, unit, scale, precision} shape with formatting owned by the frontend. Unresolved as of this writing.
  2. Pillar-specific headline cards - which two metrics should replace the Executive Overview's middle two headline cards for each of the six pillars, once all six pillar dashboards are built. Blocks full dynamic pillar behavior.

Anyone picking up backend work on this contract should treat docs/api-documentation.html's "Open questions" section as a live checklist, not historical notes.

5.3 The Honesty Gap Between "Implemented" and "Specified" - Worth Reading Carefully

This is the most distinctive thing about this codebase relative to a typical frontend repo: docs/database-structure.md has an entire Part 3 - Not yet implemented, per the M300 KPI Matrix, documenting real structure from the actual source workbook (docs/EMRC - M300 KPI Matrix v2-0 2026-06-29.xlsx) that has no code behind it yet. Rather than duplicate that section in full (it's long and the source doc is authoritative), here's what it covers and why each gap matters:

Gap What's missing Why it matters
Full KPI Registry 86 real KPIs specified, only 16 implemented. Missing fields include Likely Data Owner (distinct from sourceInstitution), separate Primary/Secondary Data Source, Data Collection Method, Data Format, full Calculation Logic, per-KPI Visualization Type, Decision Use narrative, and a Confidence Level dimension entirely separate from Validation Status The dashboard currently shows a fraction of the real indicator set, and even implemented KPIs are missing traceability fields the real registry specifies
Evidence Basis A vocabulary for "what backs this value" (Published Report / Agency Submission / Derived Value / Workbook Reference / Validation Note / No Evidence, each with required supporting fields) - nothing in the app captures this today A proposed KpiTargetRevision entity (versioned baseline/target, tied to the existing AuditEvent log) is discussed in the docs but not built
CPR Master A parallel Compact Progress Report action-tracking sheet, structured differently from the implemented BottleneckRecord - notably, "Risk / Bottleneck" in the real sheet is a field on an action row, not a first-class entity the way this codebase built it The docs explicitly flag this as a design discussion needed before building - Programs' bottleneck model may need to fold into a CPR-style action tracker rather than stay a separate register
Stakeholder Map A richer institution model with Mandate, Data Relevance narrative, Likely Access Pathway (e.g. "publicly available" vs "requires formal data request"), and Sensitivity Level - none modeled on the implemented Institution The "Likely Access Pathway" concept is exactly what real RBAC needs and isn't captured yet
RBAC enforcement ScopeAssignment models the shape but nothing reads it (§8.3) The sidebar renders every ready nav item for every logged-in user regardless of role or scope; no query filters by institution
Data Source Mapping A many-to-many map between data sources and the KPIs they feed, with an explicit gap flag Currently implicit, buried in each KpiCatalogueRow.sourceDataset string
Reports & Exports, Compact pillar dashboards (4 of 6) Nav items exist with ready: false; no schema or page Visible in the architecture, not pretending to exist

This gap analysis is a genuinely useful artifact for anyone scoping remaining work - it's effectively a backlog written in data-model terms rather than ticket terms.

6. API Contract

The full, current contract lives in docs/api-documentation.html, generated against the Zod schemas and verified endpoint-by-endpoint against the mock handlers - treat it as the live source of truth. This section summarizes the shape and the conventions that govern every endpoint, so a reader understands how to read that document rather than duplicating its content wholesale.

6.1 Conventions

Convention Rule
Base URL Everything under /api, configurable via VITE_API_BASE_URL
Content type application/json both directions
Timestamps ISO 8601 with timezone (e.g. 2025-10-14T09:12:00Z); rendered in Africa/Lagos by the frontend
Errors Non-2xx with {"message": "human readable"} - the frontend displays message directly, so it must be written for an end reader, not a log
Empty vs. zero 0 is a real value, always rendered as 0. null is used only where the schema explicitly allows it and always means "not applicable," never "zero" (§4.4)

6.2 Endpoint Inventory

Endpoint Purpose
GET /api/filters Global filter bar option lists (reporting periods, pillars, institutions) - cached client-side for the session
GET /api/executive-overview Compact leadership view - four headline cards, access-delivery channels, national performance bullets, delivery status (§6.3)
GET /api/kpi-explorer Paginated/filterable indicator catalogue, plus catalogue-wide summary and distribution stats
GET /api/kpi-explorer/kpis/:id Full profile for one indicator, fetched on drill-down (heavier payload, not loaded per catalogue row)
GET /api/kpi-explorer/filters KPI Explorer's own eight filter option lists - distinct from the global filter bar
(Programs, Bottlenecks, Data Submissions, Stakeholders, Administration, State & DisCo) Contracted via their respective schema files in src/api/schemas/; each follows the same pagination and error conventions

6.3 Executive Overview - Worked Example of Contract Rigor

This endpoint is worth walking through once because it demonstrates the level of precision the whole contract is held to:

  • appliedPillar - the backend must echo back which pillar it actually calculated for (all for All Pillars), so the frontend can confirm the server applied what was asked rather than assuming.
  • Section A (headlineCards) - exactly four, as named fields, not an array. A missing card is a validation failure, not a rendering gap. One card (accessRate) requires a sourceYear because it's an annual official publication and must never be mistaken for current-period data.
  • Section B (accessDelivery) - three channels in a fixed order (grid-connections, mini-grid-connections, solar-home-systems), with real named targets from the source workbook (750,000 mini-grid connections by 2030 under DARES; 2.75M Solar Home Systems by 2030) - and an explicit instruction that grid connections have no approved target, so target must be null, never derived from the 9% access-rate commitment.
  • Section C (nationalPerformance) - six bullet metrics, each with its own scaleMin/scaleMax because the metrics aren't comparable (a percentage, a naira total, and a loss rate share no axis), with scaleMax > scaleMin enforced by the schema.
  • Section D (deliveryStatus) - ongoingProjects[] must exclude completed records; statusSummary[] counts are backend-calculated (never averaged) and rendered directly by the donut chart; exceptions[] are ranked by severity/impact/days-unresolved, capped at 5 displayed (more may be sent, extras are simply unused).

6.5 Pagination Envelope

Shared by every paginated list in the app:

{
  "items": [ /* current page only */ ],
  "page": 1,
  "pageSize": 25,
  "total": 312   // total matching records across ALL pages, not items.length
}

Query params: ?page=1&pageSize=25.

6.6 Open Questions the Backend Team Still Needs to Answer

Documented directly in docs/api-documentation.html §16 (Open questions), and worth surfacing here since they materially affect anyone building against this contract:

  1. Auth scheme - not yet specified; the frontend assumes a bearer token on every request pending confirmation.
  2. Sorting - currently client-side over the returned page only (so sorting page 1 of a paginated table sorts 25 rows, not the full result set). Server-side sorting via ?sort=<column>&order=asc is proposed but not confirmed, including which column identifiers the backend will accept.
  3. Pre-formatted values vs. structured values - §4.6.
  4. Pillar-specific headline cards - §4.6.

Resolved, for reference: pagination convention (§6.5) and filter reach for Executive Overview (only period/pillar/institution - module-specific filters like geography/DisCo/technology live on their own endpoints).

7.3 Executive Overview

The Compact leadership landing page. Four fixed headline cards, three access-delivery channel rows, six national-performance bullet metrics, and a delivery-status panel combining a searchable/paginated project table, a Nigeria map (lat/long per project), an Apex donut for status counts, and a ranked exceptions list. Full contract detail in §6.3.

7.4 KPI Explorer / Directory

The authoritative indicator catalogue. Real registry IDs (e.g. M300-FVU-001) are first-class here for traceability but - per the specification - must never appear on executive or pillar cards, keeping leadership-facing views free of internal ID clutter. Drill-down into a single KPI (GET /api/kpi-explorer/kpis/:id) loads a heavier four-panel profile: metadata, values/history (trend chart), traceability, and linked delivery records - fetched separately from the catalogue row specifically so the list view stays light.

Currently surfaces 16 of the real registry's 86 KPIs (§5.3).

7.5 Pillar Dashboards

Per-pillar deep dives. Two of six are built (Generation & network, Last-mile access); the remaining four are visible in navigation but disabled (READY_PILLARS set), so the full six-pillar information architecture is reviewable without pretending unbuilt pages exist.

7.6 Programs (formerly three separate modules)

The most structurally significant consolidation in the app: what the original wireframe specified as three top-level pages - Implementation Register, Bottlenecks & Exceptions, and (implicitly) a Projects view - is now one drill-down hierarchy: Programs → Programme detail → Project detail, with bottlenecks and milestones surfaced as part of a project's detail page rather than as their own top-level destination.

ProjectRecord is aligned field-for-field to the real Programme & Project tracking workbook's "Project Register" sheet (§5 data model doc has the full column mapping) - meaning this is the module closest to matching a real downstream data source rather than an idealized shape.

Two things explicitly dropped in this consolidation, per the docs: a standalone Actions tracker entity, and bulk import/export of the register.

7.7 Bottlenecks & Escalations

No longer a standalone route - reached only via a project's detail page. BottleneckRecord carries category, severity, pillar, and lifecycle stage; EscalationRecord tracks decision-required items with an owner, due date, and days-overdue. §5.3 flags that the real underlying system (the CPR Master sheet) models a "bottleneck" as a field on an action row, not a first-class entity the way this codebase built it - a design tension worth resolving before this module grows further.

7.8 Data Submissions & Validation

The workflow module: Obligation (a dataset an institution owes, on a schedule) → Submission (what they sent) → Validation Queue → Decision (approve/provisional/return/reject). An approval decision publishes KpiExtraction[] - the join back into KPI Explorer, writing a new KpiHistoryPoint and an AuditEvent. Manual-entry forms and file-upload templates are both driven by schema-declared definitions (ManualEntryDefinition/UploadDefinition) rather than hardcoded per-obligation forms.

7.9 Stakeholders & Institutions

Institution registry (type: ministry/agency/regulator/utility/disco/programme-team/partner) plus CustodianAssignment - who owns which dataset, on what frequency, reviewed/validated by whom. §5.3 notes the real Stakeholder Map source has a richer model (mandate narrative, data-relevance narrative, access pathway, sensitivity level) not yet captured here.

7.10 State & DisCo Performance

A wide comparison-table module - state-level coverage, utility service-band operations (Band A–E), delivery milestones per utility, and DisCo-level metering/billing/collection metrics. Deliberately built with display-formatted string values rather than raw numbers, since its job is a dense comparison table, not a drill-down profile.

7.11 User Access & Administration

Account registry, role definitions (with a fixed Permission set: view/submit/edit/validate/approve/export/administer), scope assignments, and an audit log already receiving real cross-module events (e.g. a Data Submissions publish action writes an AuditEvent). Deliberately excluded from the global filter bar - narrowing a user registry by Compact pillar doesn't mean anything.

Branding (branding.ts) lives as a tab on this page (Customization), system-administrator only: one active site-wide BrandConfig - country name, three colours, logo, and a Google Fonts family per heading level plus body text - editable and applied across the dashboard immediately, no rebuild. Not a list of switchable presets: redeploying for another Compact country means editing this one record. GET/PUT /api/branding, PUT /api/branding/fonts, POST /api/branding/logo - see docs/api-documentation.html §5.

7.12 Reports & Exports

Nav item exists (ready: false); no schema or page yet. §5.3 notes the KPI Matrix's per-indicator Visualization Type field would likely drive what this module renders once built.

8. Authentication & Access Control

8.1 Auth Flow (as currently contracted)

Auth has no persisted entity of its own in the data model - it's a thin request/response layer against Administration's UserAccount:

Schema Fields
IdentifyAccountRequest email
IdentifiedAccount email, displayName, institution
LoginRequest email, password
LoginResponse accessToken, user: {id, name, email, role}
ForgotPasswordRequest / Response email / message

Three routes back this: /account/login, /account/password, /account/forgot-password - all outside the authenticated AppShell, per the route table (§7.2).

Open item, carried from §6.6: the actual auth scheme (bearer token assumed, not yet confirmed by the backend team) is unresolved. Anyone integrating a real backend needs this settled first.

8.2 Role & Module Access - Defined, Partially Wired

Seven system roles exist in the SystemRole enum: system-administrator, institutional-data-provider, data-reviewer, validator, dashboard-manager, oversight-user, read-only-user.

src/features/auth/role-access.ts maps each role to the nav moduleKeys it can reach, derived from the real role definitions in the mock data:

Role Reachable modules
system-administrator all (sentinel)
institutional-data-provider data-submissions, programs
data-reviewer data-submissions, kpi-directory
validator data-submissions, kpi-directory
dashboard-manager executive-overview, pillar-dashboards, state-disco, programs, kpi-directory, reports
oversight-user executive-overview, pillar-dashboards, reports
read-only-user executive-overview

canRoleReachModule(roleSlug, moduleKey) is the check function this table backs.

8.3 The Gap: RBAC Is Modeled, Not Enforced

This is the single most important caveat in the whole codebase, and it's stated plainly in the project's own docs:

ScopeAssignment already models "this user is scoped to this DisCo/programme/dataset," but nothing enforces it: the sidebar renders every ready nav item for every logged-in user regardless of role or scope, and no route or query filters by the current user's institution.

Concretely, canRoleReachModule exists as a function but - as of this documentation pass - the sidebar and route guards do not appear to call it to actually hide/block anything; the shape is there, the enforcement isn't wired in. Building real enforcement means, per the project's own stated plan:

  1. A current-user context - decode LoginResponse.user, look up RoleDefinition.modules and the user's ScopeAssignment[].
  2. Sidebar filtering by RoleDefinition.modules (using the moduleKey already on every NavItem).
  3. Query-level filtering by scope - e.g., an Institutional Data Provider scoped to a specific DisCo should only ever see that DisCo's obligations/submissions.
  4. Per-institution template generation for Data Submissions - an agency should download a template scoped to its own expected KPIs only. This is explicitly noted as having been requested directly in a stakeholder meeting, so it's a known, named requirement, not speculative scope.

Practically: anyone deploying this app in any capacity beyond an internal demo needs to treat this as launch-blocking, not a nice-to-have - the scoping model existing in the schema can create a false impression that access control is handled when today it is not.

9. Design System

Fully documented in the repo's own docs/design-system.md; this section is a condensed map plus the reasoning behind its more opinionated choices.

9.1 One File Owns Every Visual Token

Edit src/styles/theme.css. Nothing else.

Every color, font, type step, radius, and shadow used anywhere in the product is declared in that one file. Components consume them only through Tailwind utilities and never hardcode a raw value - so re-theming the entire app is a single-file change. Token names are asserted directly by component tests, so a renamed or removed token fails the test suite loudly instead of silently rendering an unstyled element.

Token group Prefix Purpose
Brand --color-brand-50…900 Active navigation, primary actions
Delivery status --color-status-* On track / at risk / lagging / delayed / blocked / no-data
Data confidence --color-confidence-* Confirmed / requires validation / future gap
Trend --color-trend-up/down Improving vs. worsening movement
Surfaces --surface*, --border-*, --text-* Declared twice (:root / .dark), swappable
Type scale --text-2xs…4xl One step tighter than stock Tailwind
Shape --radius-card/control/pill
Elevation --shadow-card/raised

9.2 Light/Dark Without Component Changes

Surface tokens are declared twice - :root for light, .dark for dark - and re-exported through @theme inline so a utility like bg-surface resolves correctly per theme automatically. A dark-mode toggle would be a single dark class toggle on <html>; no component would need to change.

9.3 Conventions Worth Internalizing

  • Never hardcode a color. bg-white text-[#101828] is wrong (invisible to re-theming, wrong in dark mode); bg-surface text-text-default is right.
  • Cards are borderless. Separation comes from surface contrast + soft shadow, per the wireframe. Three variants: default (white, shadow), well (grey container grouping white cards), plain (white, no shadow, for nesting inside a well).
  • Status color is not a free styling choice. DeliveryStatus/DataConfidence/SourceTag are closed unions with centrally-mapped colors (status-badge.tsx) - adding a status value is a contract change requiring the union, the color map, docs/api-documentation.html, and the page spec to all update together.
  • Trend arrows encode two independent things - direction the value moved, and whether that movement is good (§4.3).
  • Icons are named, not imported, by the API. A payload carries icon: MetricIconName; names resolve to Lucide components in src/config/metric-icons.tsx. An unknown name degrades to a neutral icon rather than a blank space - the backend never needs a dependency on the icon library.

9.4 Density Is a Deliberate Choice

This is explicitly designed as a dense operational tool viewed at 100% zoom for long stretches - type scale sits roughly one step below stock Tailwind, card padding is p-4 rather than p-5. Notably, the root font size is not overridden (html { font-size: 14px } was considered and rejected) specifically because that would break users who rely on browser font-size preferences; the type scale is tightened instead so rem units keep honoring user settings. This is a small but meaningful accessibility decision worth preserving in any future density changes.

9.5 Component Placement Rule

A component graduates from src/features/<feature>/components/ to src/components/ui/ on the second page that needs it - not before, to avoid premature abstraction.

10. Public Gateway

A distinct, currently-in-research area, documented in docs/public-gateway-research.md, worth including here because it defines a page with a very different audience and job than the rest of the app.

10.1 Why It's Architecturally Different

Every other module in this app is seen only by logged-in users. The public gateway (/, pre-login) is seen by everyone else - state officials, DisCo engineers, journalists, donors, ordinary citizens - and per the research doc's own framing, "has to read as official and credible before it reads as good-looking."

10.2 Working Thesis

The strongest asset this page has that Mission 300 Africa, GEAPP and most national portals don't - a live, already-built platform of real KPI data behind it. The landing page shouldn't invent generic marketing claims; it should surface the same real numbers Executive Overview already shows, a tier down in detail, in public view.

12. Quality & CI

12.1 Local Gates (Husky)

.husky/pre-commit and .husky/pre-push hooks run quality commands locally before code leaves a developer's machine (exact commands per hook weren't enumerated in this pass - check .husky/ directly for the current hook bodies, since these are the kind of thing that gets tuned over time).

12.2 CI - GitHub Actions (quality.yml)

Runs on every pull request and every push to main:

checkout → install pnpm → setup Node (from .node-version, pnpm-cached)
  → pnpm install --frozen-lockfile
  → pnpm audit --prod
  → pnpm typecheck
  → pnpm lint
  → pnpm test
  → pnpm build   (with VITE_DATA_MODE=mock)

Concurrency is configured to cancel superseded runs on the same ref (cancel-in-progress: true), keeping CI fast on rapidly-updated PRs. Notably, the production build itself runs in mock mode in CI - meaning a green CI build is a build against the mock contract, not a live-backend smoke test. This is consistent with the project's frontend-first, contract-first posture (§1.2), but worth knowing: CI passing does not verify compatibility with any specific real backend deployment.

12.3 Test Stack

Vitest + Testing Library (@testing-library/react, @testing-library/user-event, @testing-library/jest-dom), jsdom environment, MSW's Node server (src/mocks/server.ts) standing in for network calls during tests - separate from src/mocks/browser.ts, which is the browser-based worker used in actual dev/mock-mode running of the app.

13. Deployment

13.1 Vercel

vercel.json is minimal - a single SPA rewrite rule:

{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }

This is a standard client-side-routed SPA deploy: every path falls through to index.html, and React Router's data router takes over client-side routing from there. There's no build-time environment configuration visible in vercel.json itself - VITE_DATA_MODE and friends would need to be set as Vercel project environment variables to control which mode a given deployment runs in (mock for a public demo, backend once the real API is ready).

13.2 Deployment Modes in Practice

Given the three-mode architecture (§2.1), there are three meaningfully different ways this app could be deployed:

Deployment VITE_DATA_MODE Use case
Fully mocked demo mock Stakeholder review, design sign-off, no backend dependency at all
Demonstration deployment hybrid Real modules hit the live gApp backend; unfinished modules stay mocked so the full app is still walkable end-to-end
Production backend Once the backend implements the full docs/api-documentation.html contract

The README is explicit that hybrid is a transitional state - "use only for the demonstration deployment while backend coverage is incomplete" - not a long-term production configuration.

14.2 What Makes This Codebase Distinctive

Worth naming directly, since it's unusual enough to be worth flagging as a strength: most frontend repos treat their mock layer as scaffolding to be deleted once a real backend exists. This one treats the mock layer as the executable form of the contract itself - the docs say so explicitly, and the structure backs it up (schemas define the contract, mocks satisfy it and are asserted against it in CI, docs/api-documentation.html is written against the schemas, not the other way around). The practical effect is that this repository can genuinely function as the spec a separate backend team builds against, rather than a throwaway prototype - which is a meaningfully different (and harder to get right) engineering posture than a typical "mock now, wire up later" frontend.

14.3 Known Gaps / Follow-Ups (consolidated)

  1. RBAC is modeled but not enforced - sidebar and routes don't currently filter by role/scope despite ScopeAssignment and canRoleReachModule existing (§8.3). Treat as launch-blocking for any non-demo deployment.
  2. 86 vs. 16 KPIs implemented - the real registry is far larger than current coverage, with several traceability fields (Confidence Level, dual data sources, Decision Use) not modeled at all (§5.3).
  3. CPR Master vs. BottleneckRecord modeling mismatch - the real source system appears to model a bottleneck as a field on an action row, not a first-class entity; needs a design discussion before the Bottlenecks module grows further (§5.3, §7.7).
  4. Two open contract questions unresolved: pre-formatted vs. structured metric values, and which two metrics fill the middle headline cards on each of the four unbuilt pillar dashboards (§4.6, §6.6).
  5. Auth scheme unconfirmed - bearer token assumed, not verified with the backend team (§6.6, §8.1).
  6. Server-side sorting not implemented - paginated tables sort client-side over the current page only, so sorting page 1 sorts 25 rows, not the full result set (§6.6).
  7. Reports & Exports and four of six pillar dashboards have no page at all yet - visible in navigation as disabled, not hidden, per the project's stated convention (§5.3, §7.5, §7.12).
  8. CI builds and tests exclusively against mock mode - a green pipeline doesn't verify compatibility with any live backend deployment (§12.2).

14.4 Glossary

  • Compact - Nigeria's Mission 300 National Energy Compact, the overarching commitment this whole platform tracks.
  • Pillar - one of the six fixed thematic areas the Compact organizes around (§4.1).
  • Readiness tier (core/supporting/future) - how central a KPI is to the current monitoring priority, distinct from whether it's validated.
  • Validation status - where a submitted or catalogued value sits in the confirm/provisional/pending/data-gap lifecycle; not the same axis as readiness or confidence.
  • Contract - the Zod schema definitions in src/api/schemas/, treated as binding between frontend and backend (§2.5).
  • Hybrid mode - the transitional deployment state where some modules hit a real backend and others remain mocked (§2.1).
